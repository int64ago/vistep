<h2 id="understand">根不是把短码简单拼起来</h2>

四项内容先分别成为叶哈希。叶输入是 `0x00 ∥ UTF-8 内容`；内部节点输入是 `0x01 ∥ 左哈希的原始字节 ∥ 右哈希的原始字节`，都使用 SHA-256。不同前缀分隔叶与内部节点，左右顺序也属于承诺的一部分。

画面缩短哈希只为可读，内部保存并比较全部 256 位。先合成 AB 与 CD，再合成根，根就绑定这四项的顺序与内容。哈希不是加密，不能靠根恢复原文，也不会证明原文叙述真实。

<h2 id="try">验证 C，不必收到 A、B、D 的全部内容</h2>

要验证 C，只需要 C 的内容、D 的叶哈希、AB 的子树哈希，以及事先可信的根和对应位置/树大小。先将 C 与右兄弟 D 合成 CD，再把左兄弟 AB 与 CD 合成根。这次是两个兄弟哈希，而不是传送其余三项原文。

自由探索可选 A–D、修改收到的内容并重新验证。选择哪一项会改变左右组合次序。原模型还支持不满二次幂的树，按小于 n 的最大二次幂拆分，不通过复制末叶补齐；包含证明也检查索引、树大小和预期路径形状。

<h2 id="deeper">自洽不等于来源可信</h2>

<details>
<summary>篡改、替换根与证明范围</summary>

把 gamma 改为 Gamma，会改变该叶、CD 与根，其他子树哈希不变。沿原证明重建的根与原先可信根不符，验证失败。在 SHA-256 的抗碰撞假设下，这能检出与该根不一致的内容，但不是无条件、绝对的“任何修改都数学上不可能碰撞”。

如果对方连根也换成新树的根，修改后的内容和证明可以重新自洽。问题是新根从哪里来。根需由签名、可信通道或其他认证流程建立信任；包含证明本身不认证发布者，也不证明日志一直只追加。后者需要另外的连续性证明。

本例沿用 RFC 的哈希域与递归分割方式，旁注左右和范围方便教学，并非完整证书透明度协议或网络消息编码。四叶树的证明有两项；一般树包含路径规模为 O(log n)。生成整棵树仍需读取所有叶，不能把验证短证明的成本说成首次构建成本。

</details>

资料：[RFC 9162，2.1 节 Merkle Tree Hash 与 Inclusion Proofs](https://www.rfc-editor.org/rfc/rfc9162.html#section-2.1)。SHA-256 运算复用本仓库独立实现，并另与 Node 标准密码实现核对。
