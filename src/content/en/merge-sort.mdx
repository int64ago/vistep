<h2 id="understand">Splitting helps only if we can merge the pieces</h2>

Mergesort divides a sequence into smaller runs. A one-item run is already sorted, and two sorted runs can be combined into a larger sorted run. This scene uses a bottom-up version: run length grows through 1, 2 and 4, keeping the data movement more prominent than a recursive call stack.

Only the two heads need to be compared. Each run is sorted, so no hidden item can be smaller than its own head. The smaller head is therefore the least remaining item overall. Remove it, expose the next head, and use the same argument again.

<h2 id="try">Track item identity as well as value</h2>

The number beside each value records its original input position and survives every move. The two 3s come from positions 2 and 4. Taking from the left run on equality keeps position 2 ahead of position 4. That is stability in this implementation.

Exploration offers mixed, reverse and duplicate-heavy inputs. Select a pass, a merge within that pass, and an output step. Heads, output, identities and comparison counts come from one deterministic model. Seeking never loses or duplicates an item.

<h2 id="deeper">The sorted-run premise cannot be dropped</h2>

<details>
<summary>A hidden 2 and the cost of extra storage</summary>

The last chapter deliberately combines an unsorted left run `1, 4, 2` with `3, 5`. Blind head comparisons produce `1, 3, 4, 2, 5`. The hidden 2 breaks the argument. This controlled counterexample is not a valid mergesort operation; the public merge function rejects unsorted runs.

An auxiliary output array is used, and the teaching model retains history snapshots. This is not an in-place sort, and those snapshots should not be confused with a minimal implementation's memory use. Standard array mergesort takes O(n log n) time under constant-cost comparisons and O(n) auxiliary storage; this presentation stores additional history.

Stability matters when items have more than one field and an earlier ordering must be retained among equal keys. The tie-breaking rule is part of the implementation contract; not every merge variation automatically preserves stability.

</details>
